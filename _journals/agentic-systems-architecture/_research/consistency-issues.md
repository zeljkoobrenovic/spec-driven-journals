# Consistency Issues — canonical resolutions

Cross-chapter and cross-source resolutions. **These rulings win** over the interview sources and over individual chapters. Writers: when you adopt or depart from an interview design, follow these. Append new items at the end (numbered).

## From the interview-source digests (2026-10-28)

1. **"Harness" has one meaning in this book.** A *harness* is the deterministic code around a model that runs the loop, exposes tools, enforces budgets and permissions and records the run (a coding CLI is a harness; Forge is a headless harness). The sources use "harness" for three different things; say "evaluation harness" explicitly when you mean the eval runner.
2. **Isolation strength follows autonomy and code provenance.** Model-written code that runs unattended (Forge, cloud tasks) runs in a **microVM or gVisor-class sandbox**, not a plain container; containers are acceptable for trusted build steps. The ai-coding-cli design's container-only cloud sandbox is noted as a departure the book does not adopt. Local interactive CLIs use OS sandboxes (Seatbelt, bubblewrap) plus permission rules.
3. **Credentials are brokered, never placed in context, and short-lived in sandboxes.** The book's default: the tool broker (Toolyard) holds credentials and injects them at the call; a sandbox may hold only a scoped, short-lived token (e.g. a repo-scoped token valid for the run). Local CLIs acting as the user are named as **ambient authority** and mitigated with permission rules and sandboxing.
4. **Exactly-once effects, not exactly-once delivery.** Use the phrase "exactly-once effect" (at-least-once execution + idempotency key + receipt lookup). Never claim exactly-once delivery. Evidence is **not** written "in the same transaction" as an external side effect: the pattern is *intent record → execute with idempotency key → receipt record*, with reconciliation for the unknown state.
5. **Unknown outcome is a state.** After a timeout with no receipt, the action is `unknown`: check status with the idempotency key; if still unknown, escalate to a repair queue — never re-ask the model and never blind-retry a non-idempotent call.
6. **Approval semantics (one model for the whole book).** An approval is a **record bound to the exact action object version (content hash)**, with approver identity, the evidence shown, a scope and an **expiry**. It is re-checked immediately before execution; if the action object, the policy version or relevant source facts changed, the approval is void. Support's time-based expiry, sales' no-expiry and marketing's claim-library expiry are all instances: book rule = expiry by time **and** invalidation on change of action, policy or evidence.
7. **The deterministic rule layer.** In high-stakes designs the rules layer (eligibility rules, clinical contraindication checks) is authoritative: the model may **draft, explain and gather evidence** but cannot override a rule; an adverse outcome for a person (denial, reduction, clinical contraindication override) always requires a human decision. Healthcare's "veto", benefits' "decide" and research's "screen" are described as one pattern: *rules bound the model; humans own adverse decisions*.
8. **Abstention is a valid, first-class outcome** in every domain (not only healthcare): every agent has a defined "cannot answer / not enough evidence → escalate" exit that counts as success in evaluation when correct.
9. **Agent version manifest includes the exact model id** (the platform source omitted it). See [[versioning-agent-systems]].
10. **Kill switches hold, not drop.** A kill switch stops new side effects and holds queued actions for review; it does not silently discard work.
11. **Suppression and consent.** Customer-operations chapters model both: a global **suppression list** (do-not-contact) and **consent by purpose**; either one blocks an outbound action.
12. **Multi-agent research decomposition** is not covered by the interview sources; chapters 10 and 12 rely on the `orch` brief (published engineering reports and papers), and say so.
13. **Interview REVIEW.md files predate the current JSON.** Cite the JSON (with step) as the design; cite REVIEW.md only for the author's own critique.
14. **Staging store for agent output.** Agent proposals (draft entries, redlines, screening recommendations) live in a staging store separate from the system of record; only an approved action object crosses into it, executed by deterministic code.
15. **Authorization is separate from execution.** The policy enforcement point (Bulkhead) decides; the tool broker (Toolyard) executes with brokered credentials. The interview designs' "identity broker that also executes side effects" is a departure the book does not adopt.
16. **Decision record vs raw reasoning.** The evidence log keeps a curated, versioned decision record (inputs by reference, tool calls, receipts, approvals, outputs, versions). Raw model reasoning/thinking text, if retained at all, is stored separately with tighter access and shorter retention — and is never treated as a faithful explanation.
17. **Machine checks and human overrides.** A human may override a machine check only with a recorded reason; the override is a new record and never overwrites the machine verdict.
18. **Hash-chaining.** The book's evidence-log default is append-only with tamper evidence (hash chain or WORM storage) for back-office and high-stakes domains; plain append-only is acceptable for low-consequence agents. Do not claim all interview designs hash-chain.
19. **Turn vs exchange.** A **turn** is one runtime cycle: one model call plus the tool calls it proposes (owned by [[agent-runtime]]). One user message and the agent's reply is an **exchange** (it may take several turns). Latency budgets for chat are per exchange ("time to first visible response"). Reviewers align chapters that use "turn" for exchange.
20. **Forge's split (final ruling).** A Forge run is a Keelson Runtime workflow (task record, budget, approvals, credentials proxy, PR creation, Logbook) that runs the **inner coding loop inside the per-run microVM as one leased, heartbeated activity**. Model calls from inside the sandbox leave only through the egress proxy to Keelson Gateway; no credentials live in the sandbox beyond a run-scoped repo token. Chapters 07, 21 and 41 follow this.
21. **Credit limits.** Answerdesk may issue **at most one service credit per technician visit** (business key: visit id + reason code), and a ticket may have **at most one active (pending) credit proposal at a time**. Chapters saying "one credit per ticket" are aligned to this wording.
22. **Delegation token claims follow RFC 8693:** `sub` = the principal served (user or tenant), `act` = the acting agent run. The agentic-platform-foundations interview design reverses these (`sub=agent, act=user`); the book follows the RFC and notes the departure where the design is cited.
23. **Answerdesk manifest label.** The October 2027 Answerdesk production manifest (the one with credits ≤ €250 at A2) is labeled **`ad-2027.10.2`**; chapters that say `2027.10.1` for the same manifest are aligned. Manifest labels use `<agent-prefix>-<yyyy>.<mm>.<n>` (ad, cw, dr, pp, cl, sc, fg).
24. **Fixture Purge dates (owned by [[domain-coding-agents]]).** Noticed by a reviewer **Friday 16 July 2027**; Forge test-touching tasks held that day; re-enabled **Monday 9 August 2027** after protected paths and the test-count grader shipped. Chapter 25 aligns to these dates.
25. **A1 credit approval expiry is 4 hours** (owned by [[human-oversight-and-bounded-autonomy]]). Chapters saying 24 h for A1 credit approvals are aligned. Manifest labels always carry the agent prefix (`cw-2027.09.3`, `ad-2027.10.2`), per item 23.
26. **Injection suite size.** Sounding's prompt-injection suite has **1,200 variants** (owned by [[prompt-injection-defense]]); the Answerdesk release and promotion gate runs a fixed **200-case stratified sample** of it ("0 of 200 injections succeeded"). Chapters say which one they mean.
27. **Employment decisions are A0 at Ostrell.** The general policy cap for irreversible external commitments is A1, but Ostrell sets decisions about an employee (performance rating, pay change, termination, hiring) at **A0**: no agent proposes them as action objects; Peoplepoint refuses and routes to HR. Drafting non-decisional material (e.g. a performance-summary draft the manager rewrites, the November 2027 request in [[domain-high-stakes-decisions]]) is an internal draft, not a decision, and stays outside any action class until Legal approves one. Chapters 43 and 44 align to this.

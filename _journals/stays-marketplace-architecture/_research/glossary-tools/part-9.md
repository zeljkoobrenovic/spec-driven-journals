| **Convergence decision** | The group-level decision, per capability and per supply segment, of what is built once, what is built behind one contract and what stays with each brand. It is recorded with an owner, a reason and a review date. | [[converging-two-marketplaces]] |
| **Shared core** | The shared engines and shared contracts that every brand in a group must use. A brand may not build its own copy of them. | [[converging-two-marketplaces]] |
| **Shared engine** | One implementation with one owner, where brand differences are expressed as policy data. It is not necessarily a shared database or a shared cloud region. | [[converging-two-marketplaces]] |
| **Shared contract** | One schema with one meaning, filled by a different engine per marketplace type. The offer and reservation contracts are examples. | [[converging-two-marketplaces]] |
| **Supply segment** | A group of supply that shares a source of truth and a unit cardinality: hotels on channel managers, professional homes on property-management systems, or individual hosts' homes. The segment, not the brand, chooses the engine. | [[converging-two-marketplaces]] |
| **Cross-type supply / cross-type routing** | Supply of one marketplace type sold by a brand of the other type, such as boutique hotels on a homes marketplace. The routing rule is that the supply segment chooses the engine, while the brand chooses storefront, commercial terms and policies. | [[converging-two-marketplaces]] |
| **Storefront / supply engine** | The storefront is the brand-facing surface (apps, web, search, ranking, page templates) that presents offers to guests. The supply engine is the catalog, inventory and connectivity that produce offers for one supply segment. | [[converging-two-marketplaces]] |
| **Cross-listing** | A storefront showing offers produced by another brand's supply engine, with the supplier's consent, usually in a labeled section of results. | [[converging-two-marketplaces]] |
| **Stays team topology** | The assignment of journeys, engines and contracts to teams across two marketplaces, using stream-aligned, platform, complicated-subsystem and enabling teams, with a stated interaction mode and end date for each important pair. It separates journey ownership from engine ownership. | [[organizing-stays-engineering]] |
| **Architecture governance (stays)** | The rules for who may change what, after consulting whom, and where the decision is recorded. For two marketplaces it sorts decisions into three classes by blast radius: team, contract and group. | [[organizing-stays-engineering]] |
| **Blast radius (of a decision)** | How many teams, brands and money flows a decision binds. It determines which decision class applies and who decides. | [[organizing-stays-engineering]] |
| **Architecture decision record (ADR)** | A short document recording context, decision, options considered, consequences and the advice received. It is kept with the code or in a shared decision log. | [[organizing-stays-engineering]] |
| **Advice process** | Andrew Harmel-Law's model in which anyone may make an architectural decision, provided they first consult the people affected and those with relevant expertise. Advice must be sought and recorded but need not be followed. | [[organizing-stays-engineering]] |
| **Stream-aligned / platform / enabling team** | Team Topologies types: a stream-aligned team owns a flow of work end to end, a platform team provides an internal product that speeds up other teams, and an enabling team helps others overcome obstacles and is meant to be temporary. | [[organizing-stays-engineering]] |
| **Cognitive load (team)** | The amount of domain and technology a team can understand and own. Team boundaries exist to keep it bounded. | [[organizing-stays-engineering]] |
| **Ownership catalog** | A register of owners for journeys, engines and contracts, used to route alerts and questions, including partner-caused incidents, to the right team. | [[organizing-stays-engineering]] |
| **Modular monolith** | One deployable service divided into domain components whose boundaries are enforced by architecture tests in the build, not by documents. | [[organizing-stays-engineering]] |
| **Strangler fig** | Martin Fowler's pattern of replacing a legacy system gradually by moving behavior into new code behind an interception point. For stays platforms it must also move reservations already made for future dates, not only new requests. | [[modernizing-a-live-marketplace]] |
| **Seam** | A point where behavior can be redirected without changing the code on either side, such as a contract, an event stream or an API facade. | [[modernizing-a-live-marketplace]] |
| **System of record** | The one system whose write decides the truth of an entity. During a migration each reservation has exactly one at any moment. | [[modernizing-a-live-marketplace]] |
| **In-flight reservation migration** | Moving a confirmed reservation whose stay has not finished to a new system of record, keeping its identifiers, version history, delivery state, payment arrangement and policy snapshots intact. | [[modernizing-a-live-marketplace]] |
| **Open book** | The set of confirmed reservations with arrival dates still ahead, which a migration must account for. | [[modernizing-a-live-marketplace]] |
| **Parallel run (stays)** | Old and new systems process the same live input and their outputs are compared. In a shadow run only the old result is used; in a dual run a share of traffic uses the new result. | [[modernizing-a-live-marketplace]] |
| **Drain** | Sending new bookings to the new system while old reservations finish their lifecycle in the old one. It is slow where booking windows are long. | [[modernizing-a-live-marketplace]] |
| **Reverse sync** | After cutover, the new system writes its changes back into the old one so remaining readers keep working and rollback stays possible. | [[modernizing-a-live-marketplace]] |
| **Point of no return** | The dated decision after which rollback is no longer supported, usually because reverse sync is switched off. | [[modernizing-a-live-marketplace]] |
| **Post-stay tail** | The period after checkout during which a reservation still needs its system of record: no-show reporting, commission invoicing, refunds after complaints, chargebacks and tax records. | [[modernizing-a-live-marketplace]] |
| **Cutover unit** | The slice of the platform that moves at once. For reservation state it is the property or listing, so that one property's reservations stay in one engine. | [[modernizing-a-live-marketplace]] |
| **Agentic booking** | A reservation created, changed or canceled by software acting for a traveler, where the software rather than the traveler made at least one of the choices (place, property, rate, dates). | [[ai-in-travel-stays]] |
| **AI governance (stays)** | The register, tool contracts, side-effect classes, booking authority and evaluation rules that control which AI uses may read or change stays data, and who owns them. | [[ai-in-travel-stays]] |
| **AI use-case register** | A register of every AI use, built or bought, with owner, consequence class, approved tools and evaluation plan. Tool registries and gateways read it at runtime. | [[ai-in-travel-stays]] |
| **Model Context Protocol (MCP)** | An open standard, published by Anthropic in November 2024, for connecting AI applications to data and tools. A marketplace can expose its domain operations to external agents as an MCP server. | [[ai-in-travel-stays]] |
| **Agent gateway / tool registry** | The gateway identifies the agent platform and the traveler behind each call, verifies booking authority, enforces quotas and records the actor chain. The registry lists the operations an AI may call, with schema, side-effect class, scopes and owner. | [[ai-in-travel-stays]] |
| **Side-effect class** | The category of a tool by what it can change: read, draft, reversible write, money or contract, and decision about a person. The class, not the model, decides the controls. | [[ai-in-travel-stays]] |
| **Human final click (handoff) / mandate** | The two booking authorities for agents. In handoff the traveler confirms on a marketplace-hosted step. In a mandate the traveler signs constraints in advance (place, dates, maximum total, refundability) and the gateway verifies each booking against them. | [[ai-in-travel-stays]] |
| **Actor chain** | The record on a reservation of who acted: traveler, agent platform, agent session and authority ID. | [[ai-in-travel-stays]] |

| **Residuality theory** | Barry O'Reilly's approach that treats a business system as unpredictable and designs it by stressing it with environmental changes rather than forecasting them. | [[evolving-the-platform]] |
| **Stressor / attractor / residue** | A stressor is any change in the environment, likely or not. The attractor is the state the business falls into under it. The residue is what remains of the architecture, and the structural change, usually a separation, that lets the next version survive. | [[evolving-the-platform]] |
| **Naive architecture / residual architecture** | The naive architecture satisfies today's requirements and assumes today's world stays put. The residual architecture is the design after many stressors have each left their residue. | [[evolving-the-platform]] |
| **Stressor analysis (stays)** | Testing a stays platform against a list of environmental changes, tracing each through the guest's promise and recording the attractor, the residue and its status: integrated, candidate, gap or survived by composition. | [[evolving-the-platform]] |
| **Combined stressor** | Several stressors hitting one guest at once. If existing residues handle it with a coordinating case and no new structure, the decomposition is sound. | [[evolving-the-platform]] |
| **Fitness function (stays)** | An outcome measure of one part of the guest's promise, taken the same way across engines and years, with an owner, a threshold, a cadence and a decision that a breach triggers. It protects the decade, where a journey SLO protects the month. | [[evolving-the-platform]] |
| **Optionality** | Paying now to keep a hard-to-reverse decision open, justified where the stressor list holds a plausible reason to reverse it. | [[evolving-the-platform]] |

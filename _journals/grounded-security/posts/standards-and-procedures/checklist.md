*The working checklist behind this record — the documentation hierarchy, standards and procedure quality bars, required document contents, and the final quality review, from the Standards and Procedures chapter of the* Defensive Security Handbook*. The Article tab carries the rationale and anti-patterns.*

## Documentation Hierarchy

- [ ] **The policy** clearly explains **why** the organization requires the control or rule
- [ ] **Standards/manuals** define **what** requirements must be followed
- [ ] **Procedures** identify **who performs activities, when, and where**
- [ ] **Work instructions, guidelines, and SOPs** explain **how** specific tasks are performed
- [ ] Each document is placed at the correct level of the documentation hierarchy
- [ ] Related policies, standards, procedures, and work instructions are clearly linked

## Standards

- [ ] Standards provide technology-specific requirements without unnecessary procedural detail
- [ ] Standards support and expand upon applicable policy requirements
- [ ] Requirements use clear, mandatory language such as **must**, **shall**, or **will**
- [ ] Ambiguous wording such as **should**, **try**, or **mostly** is avoided where a requirement is mandatory
- [ ] Requirements are specific enough to be consistently implemented
- [ ] Standards avoid duplicating detailed information already maintained elsewhere
- [ ] Common requirements are documented once and referenced by applicable policies
- [ ] Standards are maintained separately where doing so improves usability and maintainability
- [ ] Changes to standards can be made centrally without requiring unnecessary changes to multiple policies
- [ ] Standards are reviewed regularly for technical accuracy

## Procedures

- [ ] Procedures explain how standards are implemented on specific technologies or platforms
- [ ] Procedures contain enough detail for the intended audience to complete the task consistently
- [ ] Platform-specific procedures are created where technologies require different implementation steps
- [ ] Steps are listed in the order in which they must be performed
- [ ] Instructions use the active voice
- [ ] Grammar and wording are clear
- [ ] Assumptions and prerequisites are explicitly stated
- [ ] Assumptions are verified as valid
- [ ] Instructions are concise and avoid unnecessary wording
- [ ] Technical terminology and jargon are used only where appropriate
- [ ] Commands, settings, configuration values, or examples are included where needed
- [ ] Procedures allow appropriate judgment where overly prescriptive instructions would be impractical
- [ ] Procedures are reviewed by people who understand both the technology and the intended audience

## Consistency and Knowledge Distribution

- [ ] Standards and procedures support consistent implementation of organizational policies
- [ ] Requirements can be applied equally across relevant teams and systems
- [ ] Documentation reduces reliance on institutional or legacy knowledge
- [ ] Employees can locate the information they need without relying on specific individuals
- [ ] Documentation is understandable to new employees and personnel outside the original authoring team
- [ ] Documentation clearly communicates organizational expectations
- [ ] Information is organized so users can quickly find the appropriate document
- [ ] Repetition between policies, standards, and procedures is minimized

## Regulatory and Management Requirements

- [ ] Applicable laws, regulations, contractual requirements, and compliance frameworks have been identified
- [ ] Required policies, standards, and procedures exist to support applicable compliance obligations
- [ ] Relevant regulatory or legal references are included where appropriate
- [ ] Documentation can be readily provided during an audit or compliance review
- [ ] Standards and procedures have appropriate management endorsement
- [ ] Required approvals are documented
- [ ] Documentation demonstrates that responsible management has accepted the requirements

## Required Document Contents

### Version Information

- [ ] Document version number is included
- [ ] Effective date is included
- [ ] Revision or update date is included where applicable
- [ ] Current and obsolete versions can be clearly distinguished
- [ ] A revision history is maintained where appropriate

### Owner and Approver

- [ ] Document owner is identified
- [ ] Required approver or approving authority is identified
- [ ] Approval has been formally recorded
- [ ] Ownership information allows users to submit questions, feedback, or revision requests
- [ ] Responsibility for future review and maintenance is clear

### Purpose / Overview

- [ ] The document contains a brief purpose or overview
- [ ] The purpose explains what the document is intended to accomplish
- [ ] The overview allows readers to quickly determine whether the document is relevant to them
- [ ] The overview is concise and generally limited to a short paragraph where possible

### Scope

- [ ] The scope identifies who or what the document applies to
- [ ] Applicable employees, contractors, departments, systems, applications, or technologies are identified
- [ ] Any exclusions are clearly stated
- [ ] Organizational or technical boundaries are unambiguous

### Statements / Requirements

- [ ] Requirements or procedural statements are clearly identified
- [ ] Statements are concise and unambiguous
- [ ] Requirements can be objectively understood and applied
- [ ] Statements are reviewed regularly for accuracy
- [ ] Technical requirements reflect the current environment
- [ ] Obsolete instructions are removed or updated promptly

### Related Documents

- [ ] Applicable policies are referenced
- [ ] Applicable standards are referenced
- [ ] Applicable procedures, processes, work instructions, or SOPs are referenced
- [ ] Related documents can be easily located
- [ ] Applicable regulatory, legal, or compliance references are included where useful
- [ ] Cross-references are kept current when related documents change

## Naming and Organization

- [ ] Consistent naming conventions are used for policies, standards, procedures, and supporting documents
- [ ] Referenced systems, technologies, roles, and artifacts use consistent terminology
- [ ] Document names clearly indicate their purpose
- [ ] Documents are stored in an approved, accessible repository
- [ ] Users can determine which document is authoritative
- [ ] Superseded documents are archived or marked obsolete
- [ ] Access permissions are appropriate for the intended audience

## Final Quality Review

- [ ] The document is written for the skill level of its intended readers
- [ ] The document is easy to read and navigate
- [ ] Language is simple, direct, and consistent
- [ ] Requirements do not conflict with higher-level policies
- [ ] Procedures correctly implement the applicable standards
- [ ] Work instructions and SOPs correctly implement the applicable procedures
- [ ] Technical information has been validated
- [ ] The document has been reviewed by appropriate subject-matter experts
- [ ] The document has received all required approvals
- [ ] A review frequency or next review date has been established
- [ ] The final approved version has been published and communicated to relevant users

With the final quality review green, the document is publishable — versioned, owned, approved, findable, and consistent with everything above and below it in the hierarchy. The test running through the whole checklist: **could a new employee find the authoritative document and apply it correctly without asking anyone?**
